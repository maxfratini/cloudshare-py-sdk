## Integrations

### CloudShare REST API v3

mxCloudShare automates the CloudShare platform (cloud-based training and demo environments) through its REST API v3. Every CLI command and SDK helper ultimately issues HTTP requests to this API.

- **Purpose:** Create, manage, suspend, delete, and inspect CloudShare environments, VMs, snapshots, classes, students, instructors, webhooks, permalinks, teams, and analytics. The typed SDK covers approximately 46 of the ~86 documented endpoints; the generic `cs_api_call` escape hatch reaches the rest.

- **Auth:** The API uses a custom `cs_sha1` HMAC-signed authentication scheme. Each request carries an `Authorization: cs_sha1 <signature>` header computed from the API key, the URL, and a token generated by the in-house `token_generator.py` / `hmacer.py` / `authentication_parameter_provider.py` modules.

  Credentials are two values:
  - `CLOUDSHARE_API_ID` — the API account identifier
  - `CLOUDSHARE_API_KEY` — the shared secret used for HMAC signing

  They are resolved at startup via `loadKeys()` in `cli.py` with this priority:
  1. A file path passed via `--keyfile` (loaded with `python-dotenv`)
  2. `CLOUDSHARE_API_ID` / `CLOUDSHARE_API_KEY` environment variables
  3. A `cloudshare.env` file in the current working directory

  Once resolved, they are propagated into the SDK globals by `cs.cs_set_auth_keys(api_id, api_key)` in `mxcloudshare/mxcloudshare.py`. The HTTP `Requester` in `requester.py` receives the raw API ID and key on every call and builds the signed Authorization header per-request.

- **Base URL and host resolution:**

  The current code hard-codes the hostname to `"use.cloudshare.com"` in `mxcloudshare/mxcloudshare.py` line 16 (`cloudshare.req(hostname="use.cloudshare.com", ...)`). The `Requester._build_url` method constructs the full URL as:

  ```
  https://<hostname>/api/v3/<path>
  ```

  The upstream legacy wrappers (`wrapper.py` and `wrapper_cls.py`) read the hostname from a `CLOUDSHARE_HOSTNAME` environment variable, defaulting to `"use.cloudshare.com"`. The modern SDK path does not use this env var.

- **Query parameters:** The `Requester._build_url` method appends query parameters as `?key=value&key2=value2` using `urllib.parse.urlencode`. Parameters are passed as a `dict[str, str]`. The generic `cs_api_call` and the CLI's `api-call` command both accept raw query-parameter dictionaries; the typed helpers hard-code the required query params inside their function bodies.

- **Pagination:** The current code does not implement cursor/offset pagination. Some endpoints (e.g., `GET /envs/?brief=false`) accept a `brief` boolean parameter, but the API's pagination (`limit`, `offset`, `page`) is only reachable through the generic `api-call` / `cs_api_call` escape hatch.

- **Rate limits:** No rate-limit handling is implemented. The API's rate-limiting behavior is not documented in this codebase. There is no retry/backoff logic in `requester.py` or `mxcloudshare.py` beyond the polling loop in `env_wait_condition`.

- **Polling behavior (`env_wait_condition`):** Commands that wait for a status transition (suspend, resume, delete, revert) poll every 6 seconds by default (configurable `delay_secs`), with a maximum of 20 retries (configurable `max_retry`). Each poll fetches VM statuses via `GET /envs/actions/getextended`. If the target `statusText` is not reached within the retry limit, the command logs a timeout but does not fail — it returns `False` and the CLI logs a timeout message without raising an exception.

- **Error handling:** `cs_request` in `mxcloudshare.py` raises an `Exception("status message")` for any non-2xx response. The exception is unhandled at the SDK level — the CLI does not catch it, so a failed API call surfaces as an unhandled exception to the user. The upstream legacy wrappers (`wrapper.py`, `wrapper_cls.py`) print the status and content to stdout and raise a generic `Exception('Error')`. There is no structured error type or error-code-based branching.

- **Legacy-path decisions:** Two API paths in use are undocumented in the CloudShare REST API v3 reference. Per the API gap closure plan (decisions D3 and D4 in `plans/2026-10-07-api-gap-closure.md`):
  - `/blueprints` and `/policies` — These flat-list endpoints are kept working unchanged. The project also provides project-scoped alternatives (`GET /projects/{id}/blueprints`, `GET /projects/{id}/policies`) that are documented.
  - `POST /envs/actions/create` — The official documented path is `POST /envs`, but the legacy action path is kept because it works today. Changing it is a separate risk decision.

- **Docs:** The official CloudShare REST API v3 reference is at <https://docs.cloudshare.com/rest-api/v3/>.

## Local / test setup

Integration tests (`tests/test_integration.py`) require real CloudShare credentials and are skipped by default. To run them:

```bash
export CLOUDSHARE_API_ID=<your-api-id>
export CLOUDSHARE_API_KEY=<your-api-key>
uv run pytest tests/test_integration.py -v
```

All other tests run entirely offline. They mock `mxcloudshare.mxcloudshare.cloudshare.req` with `unittest.mock`:

```python
from unittest.mock import Mock, patch

def make_mock_response(data):
    mock_resp = Mock()
    mock_resp.status = 200
    mock_resp.content = data
    return mock_resp
```

The mock is patched onto `mxcloudshare.mxcloudshare.cloudshare.req` for SDK-layer tests or onto `cloudshare.req` directly for requester-layer tests. No test file reads real credentials from the environment.
